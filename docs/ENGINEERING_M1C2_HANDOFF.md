## Scope and required behavior

1. **Explicit ownership:** define validated, non-interchangeable fixture and account/store descriptors. Reusable domain/storage/sender code must not infer a server UUID from the letters A/B. Keep fixture mapping in a dedicated adapter. Namespace account files, keys and metadata by environment/account/store identity using safe validated components. Distinguish installation identity and authorization epoch from credential generation. A descriptor is not authentication authority: opening/using a store still requires a trusted access boundary and matching encrypted metadata.
2. **Preserve the fixture:** retain exact A/B filenames, SecureStore keys, `m1a.synthetic.v1` marker, owner values, migration v1/v2/v3 SQL/checksums, queued command content and hashes. No rename, relabel, copy or import into the new namespace. Existing revoked B stays revoked. Keep development opt-in and default/Release refusal. An injected permissive boundary must not make a Release fixture accessible. Use a fixture facade if needed to avoid wide UI churn.
3. **Reusable local repository:** implement UUID-owned repository behavior through injected test authority on new explicitly named synthetic test stores, with no runtime real-account entrypoint. Preserve atomic fact/history/outbox writes, draft sequences, stable result IDs, dependency order, unknown outcomes, conflicts and correction history. Validate environment/account/store/installation metadata before granting access; wrong/missing keys, existing files with missing metadata or unknown migrations fail closed without overwrite. The database encryption key remains separate from auth credentials. Avoid duplicating the full domain repository for every identity type.
4. **Durable local authorization:** implement the agreed protected-record plus encrypted-store latch protocol against explicit injected storage interfaces, using the actual SQLite transaction path in tests rather than only an in-memory boolean model. A matching authorized epoch/owner must exist on both sides before private access. Partial unlocks, partial locks, corrupt state and newer transitions stay locked. Explicit logout/switch invalidates in-memory access and pending sender work immediately; acknowledge completion only after durable lock evidence. If all lock writes fail, report incomplete logout and prevent switching. Retain records/drafts/outbox/keys. Ordinary credential expiry is not logout and must preserve independently valid local authorization.
5. **Coordinator integration boundary:** make the new account/local-store layer supply or validate the trusted expected-owner and conditional-write semantics required by M1c.1. Exercise same-account reauthorization, corrupt rotating credentials with valid independent ownership, and foreign-account rejection through the actual new boundary. No assertion that separately awaited Keychain and SQLite writes form one atomic transaction. Document serialization and restart proof explicitly. Native rotating credential adapters and production install-marker backup handling remain M1c.5; in this slice the protected-record adapter is injected/test-only. Do not install the auth coordinator into the runtime UI yet.
6. **Stale work and sender isolation:** preserve checks after awaits and at dispatch/application/commit boundaries. A stopped/old account cannot install UI state, apply an acknowledgement, update a draft, or send new work. Returning to the same verified account must recover its own queue; another account cannot consume it. Move fixture HTTP/mapping details behind the explicit fixture adapter; the reusable sender accepts a validated account identity/transport instead of A/B assumptions. No real transport or session API is implemented now.

Prefer additive modules and narrow refactors. Changes to existing App.tsx are limited to mechanical fixture-interface compatibility, not new screens, sign-in, diagnostics that unlock UUID accounts, styling or features. No new dependencies or package/runtime upgrades are expected. If the core design cannot be implemented safely within these limits, stop with the precise conflict rather than silently changing the architecture or scope.

## Local data and verification boundaries

New account-owned stores used here contain invented test records and injected authority only. Keep their namespace separate from both retained M1a fixtures and future genuine accounts. Any new SQLite migration is forward-only and applied solely to named task-owned synthetic resources; preserve existing ledgers and all retained data. Do not run PostgreSQL setup/migrations, access prototype environments or real health records, delete simulators/keys/databases, or reset fixtures to make tests pass. Prefer in-memory/disposable adapter tests; native regression runs may use the existing development simulator workflow without Apple account/signing changes or phone access.

Acceptance evidence:

- Full `npm run check` from `rebuild/` passes with all prior 88 tests and new focused tests. Exact counts and commands in the report; `git diff --check -- rebuild` passes.
- Cross-account, cross-environment, wrong-store/install/epoch/key/migration cases fail closed. Fixture/UUID namespaces cannot alias, including a UUID equal to the synthetic API account ID. No owner selection based on nickname/email/client label.

- M1c.1 F1–F5 regressions remain and are exercised across the new boundary where applicable. Unknown/corrupt independent ownership remains locked; corrupt rotating credentials alone do not erase good local data.
