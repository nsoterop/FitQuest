## Required implementation

1. **Trusted signer configuration.** Reuse installed JOSE; no new dependency. Require explicit server-supplied native client ID, Team ID, Key ID and suitable P-256 private signing key. No request-selected endpoint, audience, algorithm, key, environment or redirect URI; no secret discovery from the old prototype, disk or ambient configuration. Copy/validate configuration; do not expose keys through errors. Use ES256 for the client-secret JWT, distinct from the accepted RS256 identity-token verifier. Claims bind issuer to Team ID, subject to exact configured client ID, audience to Apple's fixed origin, with injected UTC time and a bounded short lifetime (five-minute engineering default, not production policy). Reject invalid key/config/time before dispatch. Import/construction must not perform network I/O.
2. **Native code exchange only.** POST form-encoded `client_id`, signed `client_secret`, `code` and `grant_type=authorization_code` to the fixed HTTPS Apple token endpoint. This slice has no browser redirect flow; omit `redirect_uri` rather than accepting caller input. Accept bounded nonempty authorization codes and caller cancellation. No authorization-code retry, including after timeout, 429, provider rejection, response loss or uncertain failure. Do not implement refresh/standing checks or provider revocation yet.
3. **Bounded transport.** Manual redirects with rejection, no credential forwarding to other locations, HTTPS verification intact, bounded total time through response-body consumption, explicit response byte limit, and pre-aborted/late-aborted handling. Ignored aborts or stalled/oversized bodies must not leave the public call pending indefinitely or turn a late response into success. Release/cancel readers and timers appropriately. Use a fixed-endpoint runtime factory and an explicit offline-test seam; no environment-selected fake-provider fallback. Tests must intercept every possible outbound path, including the runtime factory.
4. **Sensitive response boundary.** Validate the authorization-code success response, including identity/access/refresh token strings, token type and numeric expiry, with explicit bounds. Return a typed internal sensitive result that preserves the required provider credentials for the later protected lifecycle; it is not verified identity and must never be called authenticated or converted into a FitQuest principal. No token logging, disk/cache persistence, bearer-response cache or public/mobile response mapping. Do not trim opaque tokens or silently discard refresh/access credentials to fit the old one-field simulated port. Document handling of extra non-authoritative provider fields. Reject malformed/incomplete responses without granting authority.
5. **Sanitized failure semantics.** Distinguish malformed input/configuration, provider rejection and operational unavailability with fixed internal outcomes sufficient for a later adapter. Never echo raw bodies, codes, keys, client secrets or provider exceptions. A rejected code or provider outage is not `SESSION_REVOKED`; this module has no family binding. Do not add shared wire codes or alter domain outcomes. Identity-token cryptographic verification and pair matching remain mandatory at later integration; parsing success alone grants nothing.

Protected provider-credential encryption/storage, key-version rotation, atomic linkage to issuance, standing-check fencing and eventual revocation remain the next separately scoped integration boundary. This split does **not** waive those requirements or authorize using the new module without them. Return a precise design question if implementation needs to widen this scope.
