## Required implementation

1. **Persisted challenge.** Generate independent cryptographically random nonce/state values and a UUID challenge ID, bound to trusted server client/environment configuration and a strict server expiry. Use existing wire schemas; callers cannot select an account, issuer, client audience or environment. Store only necessary challenge metadata and protect pre-authentication access with narrow privileges. Retain case-sensitive nonce/state semantics; canonicalize validated UUID identity consistently. Configurable engineering defaults remain five-minute challenge lifetime and a thirty-second attempt deadline capped by challenge expiry. They are not approved production policy.
2. **Validation and exclusive claim.** Validate the bounded exchange request, stored challenge binding/state/deadline and native identity token through the real M1c.4a verifier before provider-code dispatch. Exclusively claim the challenge with a server-generated attempt/fence ID, an unambiguous request digest and deadline, committing that claim before invoking the injected exchange. Concurrent identical requests must not cause multiple exchanges; conflicting requests must not replace a claim. Document sanitized same-request in-progress versus reused/expired outcomes using existing auth error vocabulary. Persist digests, not replayable authorization codes or raw JWTs. Do not expose a bearer-response cache.
3. **External phase without locks.** The code-exchange port has no live transport in this slice. Tests supply generated, signed token responses and controlled failures. Neither code exchange nor JWKS verification may occur while holding a database transaction/lock or checked-out transaction client across the external wait. Bound dispatch/response time and fence late responses. No automatic retry of an uncertain code exchange; a committed claim followed by crash, timeout or lost external response requires fresh authorization, not reclaiming and replaying the old code. Do not describe a timeout as confirmed account/session revocation.
4. **Verify returned identity.** Independently verify the exchanged token against the same trusted audience and stored nonce, and require issuer/subject/audience agreement with the native token. A simulated provider response may not bypass signature checks or supply an account ID. Reject malformed/missing/substituted token responses and invalid/key-unavailable outcomes without issuing credentials. Recheck token validity as needed at finalization; the verifier's JWT tolerance must never extend strict challenge/attempt deadlines, including time spent waiting for locks.
5. **Atomic finalization.** Only the still-valid winning attempt may resolve/create the internal account and create one pending family, credential generation and revocation capability. Commit challenge completion, identity mapping and session issuance in **one checked-out PostgreSQL transaction**. Do not call the existing self-committing `issue()` and then mark a challenge consumed afterward. Factor the smallest reusable transactional issuance primitive as necessary; preserve existing synthetic issuance semantics and all M1c.3 behavior. Rollback must leave no new orphan account/mapping/family. A committed success with a lost response cannot return the secrets again or create another family on retry. Fresh authorization may resolve the same account and issue a separate family. Document what happens after a finalization rollback following a successful simulated exchange; never silently re-exchange the code.
6. **Identity, locks and isolation.** Map verified provider/issuer/subject, not email/name/native user strings. Namespace new test resources separately from old fixtures; never relabel or merge their accounts. Preserve account status/epoch enforcement and a documented consistent lock order compatible with account → session → attempt → aggregate. Initial challenge claiming is a separate pre-account transaction; finalization must not introduce the opposite attempt → account order. Include the existing identity-resolution guard in the lock analysis. Runtime roles remain non-owner/non-superuser/non-BYPASSRLS with forced RLS and owner-qualified domain queries. Pre-authentication challenge/lookup privileges cannot read athlete data. Any narrowly scoped security-definer helper needs fixed search path and explicit grants; no arbitrary caller-selected identity/account function exposed as authority.
7. **Reuse session behavior.** Issued pending credentials must remain restricted to activation/revocation. Demonstrate activation, identity/private access, refresh and logout with the existing session implementation in the new test environment. Minimal internal trusted environment/identity-boundary generalization is permitted; no request-selectable environment or fixture fallback. Preserve F1 expiry classification, F2 preflight safety and F3 UUID equivalence. Domain command serialization, hashes, receipts, outcome formats and mobile behavior remain unchanged.
