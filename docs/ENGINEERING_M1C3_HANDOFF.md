## Required scope

1. **Session storage and identity separation.** Add forward migrations for account status/authorization epoch, uniquely namespaced provider-to-internal-account identity mapping, session families, credential generations, consumed refresh operations and revocation capabilities. Keep migrations 001/002 byte-for-byte unchanged and domain history/outcome formats intact. Introduce only explicitly allowlisted test environments without relabeling existing accounts. Synthetic verified-provider input is an injected trusted test boundary, never a public account-selector endpoint. Concurrent identity resolution must not create duplicate mappings or orphan accounts. Challenge/exchange HTTP, Apple JWT/JWKS verification, provider-token storage and standing checks remain M1c.4 unless a precise dependency requires HQ clarification.
2. **Issuance and activation.** Use cryptographically random opaque access/refresh/revocation secrets via Node crypto; store token hashes, not replayable plaintext bundles. New credentials are pending, restricted to activation/revocation. Validate activation against token family/generation and server deadlines, then return the strict active identity without new secrets. Duplicate activation succeeds only for the matching still-valid active generation, including after the pending deadline when access remains valid. Enforce configurable accepted timing defaults and absolute lifetime on every operation, independent of cleanup. Production time is server-controlled; injected test time must not become client authority.
3. **Refresh and revocation.** Atomically consume refresh, record operation ID, invalidate old access and issue the next pending generation. Rollback allows the exact request to retry. A committed rotation with a lost response returns reauthentication for the same operation, never cached bearer material; another operation reusing that token revokes only its family. A delayed same-operation duplicate must not revoke the new active generation. Unknown tokens have no revocation effect. Retain older revocation-only capabilities for their own family through absolute expiry; logout is idempotent, can revoke pending/active families, and cannot affect another account or family. Do not conflate expiry, unknown credentials, provider outage and confirmed revocation.
4. **Authorization inside private transactions.** Candidate token lookup is not authority. Under a consistent account → session → operation/attempt → aggregate lock order, revalidate account environment/status/epoch, session status, credential generation and deadlines on the same checked-out transaction client before domain effects or reads. Cover command execution, stored outcome retrieval, identity, profile, session and session-list reads. Preserve original command IDs/hashes/receipts and recover previously committed outcomes under fresh authorization. Do not write authentication failures as terminal domain rejections. Avoid duplicating the domain SQL repository; retain an explicit fixture facade for the old A/B API and prevent bare-account fixture authority from opening new-account resources.
5. **Least privilege and isolation.** Force appropriate RLS, retain owner-qualified queries, and test with non-owner, non-superuser, non-BYPASSRLS runtime roles. Token lookup needs a narrow privilege boundary that cannot read athlete records. Runtime account locking must not require permission to change environment/identity. Review any security-definer helper's fixed search path and grants. Isolate token/session capabilities from domain data access; reject guessed account/session IDs and crossed credentials. No provider/network call while database locks are held.
