## Allowed changes and required behavior

1. Add a narrowly scoped provider-verification module and tests under `rebuild/services/api/src/`. Use a maintained JOSE implementation for signature and claim verification, not hand-written crypto or decoded claims treated as authority. One compatible pinned `jose` dependency and its necessary lockfile/manifests/build-compatibility adjustments are permitted. Verify current official guidance and installed/package Node compatibility; no broad ESM conversion, framework upgrade or unrelated dependency cleanup. If a wider toolchain change is necessary, report the concrete constraint before making it.
2. Require trusted server configuration for the exact native client audience and expected challenge nonce. Fix the Apple issuer and JWKS endpoint; a request or JWT header must never select its own issuer, audience, key URL or trust root. No default placeholder client ID may authorize a token. Keep generated test keys/resolvers injectable only through explicit internal test seams, never runtime environment fallback. Construction/import must not make network calls or enable routes.
3. Validate bounded compact JWT input, signature, explicit algorithm allowlist, required issuer/audience/subject/expiration and nonce, plus applicable time claims. Use injected time for deterministic tests and a documented bounded JWT clock tolerance; it must not extend future database challenge/session deadlines. Preserve subject and nonce as opaque case-sensitive strings. Account identity is provider/issuer/subject, never email, nickname, or an unverified native user value. Missing, malformed, wrong-type or mismatched claims must fail closed.
4. Return a minimal internal verified-token result, not a FitQuest account ID, bearer bundle or raw claim bag. If adding a helper to compare a native token with an exchanged token, verify both independently against the same trusted audience/nonce before comparing issuer/subject/audience. A valid token alone does **not** mean an authorization code was exchanged, a challenge was consumed, or sign-in is complete. Do not call `AuthSessionRepository.issue`, widen its synthetic input, change provider mapping or bypass future challenge fencing.
5. Use library JWKS selection/cache behavior with bounded timeout/cooldown/cache lifetime; document exact chosen semantics. Exercise it via generated public keys and an injected HTTP response transport with no real network. Follow the approved proposal's configurable engineering defaults unless official compatibility evidence requires an explained adjustment. Test unknown key IDs, key overlap/removal after cache refresh, stale/empty/malformed key sets, fetch failure and concurrency. Do not claim instantaneous key-removal detection while a valid cache exists, or silently accept indefinitely stale keys after failed refresh. Never follow token-supplied `jku`/`x5u` URLs or redirects to an unapproved trust source.
6. Distinguish invalid/unverifiable tokens from provider-key unavailability using sanitized internal results/errors. Neither is confirmed FitQuest family revocation. Do not log tokens, headers, nonce/state, provider subject, request bodies or raw provider/library exceptions; add negative leakage tests. Do not serialize an entire JWT payload into diagnostics or reports.
