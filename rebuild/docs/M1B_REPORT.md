# M1b engineering report — disposable local API synchronization

Date: 2026-09-25. Scope: local `rebuild/` implementation and verification for HQ review. This report does not claim milestone acceptance. No hosted migration, deployment, real credential, real athlete data, Apple configuration, or phone setup was performed.

## Implementation

- Added versioned PostgreSQL migrations for task-owned accounts, current aggregates, immutable revisions, durable operation outcomes, and restricted API access. RLS is enabled and forced; every repository transaction sets and clears a transaction-local owner ID. The local cluster script checks its filesystem and database markers before migration and creates separate dev/test databases over a Unix socket with TCP disabled.
- Added bearer identity injection to the Fastify app and an explicitly opted-in Debug fixture server at `127.0.0.1:3401`. The default API server remains health-only. Commands validate strict shared contracts, serialize per account/target, save the revision and operation outcome atomically, and replay an identical operation without adding a revision. Ownership and account-wide operation-ID reuse are checked before target access. Read routes return only owner-scoped snapshots with `Cache-Control: no-store`.
- Extended the existing encrypted mobile repository with additive migration v3: delivery state, confirmed bases, and sync metadata. The v1/v2 SQL and checksums remain unchanged. Commands and revisions remain immutable. The sender validates account identity and receipts, drains in dependency order, persists unknown outcomes and bounded retries, and marks conflicts for explicit review. Applying local creates a new operation at the reviewed server revision; adopting server retains drafts and history. A per-account Debug token is stored in SecureStore, never in the tracked app bundle. Local save and API sync status are distinct.
- Updated the native storage diagnostic to verify the immutable command after reopen; an active sender can legitimately acknowledge it before the diagnostic checks the pending queue.

## Verification

- Final correction-source `npm run check`: passed typecheck, lint, API build, 2 API tests, 7 contract tests, and 40 mobile tests (49 total).
- `npm run test:pg`: 9 tests passed against the disposable PostgreSQL test database. Coverage includes mixed profile/session round trip, actual HTTP and database reads, restart/replay, five transaction fault boundaries, lost acknowledgement, simultaneous duplicate retry, cross-target operation-ID race, terminal conflicts, two-account isolation, unauthorized requests, pool owner reset, and read limit validation.
- Guarded setup and verification applied both numbered migrations to dev/test databases. The fixture API started only with its opt-in and local marker. A/B tokens were generated into ignored private artifacts and not printed in the report.
- On dedicated iPhone 17 Pro simulator `FitQuest M1b Disposable`, Debug saved synthetic A offline profile plus a completed session with a 5-rep, 95 lb Squat set and a 12-minute timed interval. Nine queued operations drained to zero. Local API reads returned the profile and session at revision 8 with both activities and entries. B's API profile stayed at revision 0 with no sessions.
- Native one-shot acknowledgement failure showed **Outcome unknown · Retry same operation**, then confirmed the same operation (10 confirmed). With API stopped, a profile edit stayed saved locally and showed **Local API unavailable · Will retry**. After restarting the API it confirmed with zero pending (11 confirmed).
- A controlled revision conflict showed one blocked profile and the base revision 3, local value, and server revision 4 in native review. Selecting **Apply reviewed local record** created a replacement operation and returned to zero pending (12 confirmed). Switching to B showed no A records or token; switching back restored A's completed session and confirmed status. Native storage diagnostics then passed SQLCipher, owner/migration mismatch rollback, three write fault rollbacks, same-operation idempotence, draft separation, reopen durability, and wrong/missing-key rejection while sync was active.
- HQ correction F1: the sender now rechecks stop and fixture eligibility after awaited queue, summary, and token work, and immediately before dispatch. Closing the HTTP transport prevents dispatch after a pending token read. If eligibility ends after work is claimed, that immutable operation is durably marked outcome unknown for later recovery. Tests hold each await open and verify no late dispatch, plus recovery by a new sender. The app stops its sender on component teardown and invalidates pending attach work.
- HQ correction F2: adopting a reviewed profile with an empty draft tombstone now repopulates the editor from the stored server choice. Actual raw drafts and newer typing remain intact; late reads cannot overwrite a new account or input. The native profile conflict at local revision 8/server revision 9 adopted **Adopted server** with the server time zone and units. Returning from Details twice still showed those values; a subsequent Save advanced the API to revision 10 with the adopted values. A selected-session result conflict at local revision 8/server revision 9 adopted the 14-minute server result; Back and Correct entry both showed 14 minutes. Store tests retained the unsubmitted draft and superseded history.
- After a clean native process termination/relaunch, A's queued edit stayed local while the API was stopped and B was active; returning to A delivered it once (server revision 11 to 12). Synthetic expiry held two local edits while the API stayed at revision 12; restoring A's fixture authority drained both to revision 14. A current-source Debug rebuild succeeded (0 errors, 2 warnings). After a JS reload, native Pause held a new profile edit locally at one pending while the API remained at revision 14; Resume delivered it once to revision 15 and zero pending.
- The final-source Release simulator build succeeded (0 errors, 4 build warnings). The installed Release app showed only **Real authentication is not connected. Athlete records are locked.** on the same simulator that held Debug fixture records and authority. No synthetic entry or sync controls were visible.

## Limits and next task

- This is a synthetic, same-Mac loopback fixture. It does not establish real sign-in, hosted Supabase connectivity, physical-device reachability, background delivery, or production migration safety. The Debug API token is a disposable local test authority only.
- The Release build warnings were duplicate `-lc++` linker notices and build-tool messages; the build completed. Automated lifecycle barriers and native pause/switch/expiry were exercised; a deterministic native scheduler-level race injection and physical-device run remain unperformed.
- HQ should inspect the diff and decide M1b acceptance. If accepted, the next engineering assignment should be scoped separately; do not extend this implementation into M1c without approval.
