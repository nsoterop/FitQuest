# M1c.3 Engineering report — transactional server sessions

Date: 2026-09-26. Scope: the assigned synthetic-identity, isolated-local-PostgreSQL server increment, including HQ's bounded F1/F2/F3 corrections. This is not Apple sign-in, an authentication HTTP API, mobile integration, or production acceptance.

## Implemented boundary

- Forward migrations `003_transactional_sessions.sql` and `004_session_invariants.sql` add an explicit `m1c3.synthetic.test.v1` account environment, account status and authorization epoch, unique hashed synthetic-provider mapping, session families, credential generations, consumed refresh operation IDs, and family-scoped revocation capabilities. Migrations 001/002, original command hashes/receipts/outcome formats, and the M1b development database were not changed. The second migration narrows update grants and enforces a unique account-level consumed operation ID. Both new migrations were applied only to the marked M1c.3 test database.
- `src/authSessions.ts` is an internal repository with invented verified-provider input. It issues independent 32-byte random opaque access, refresh, and revocation secrets; PostgreSQL stores their SHA-256 hashes, never a replayable credential bundle. Pending credentials can activate or revoke but cannot read or write athlete data. Activation retries acknowledge an already active matching generation while access remains valid, including after the pending deadline. Refresh consumes the old generation and operation ID atomically, invalidates old access, and creates a pending successor. A lost committed response yields reauthentication for the same operation; different-operation token reuse revokes only that family. An old revocation capability remains valid for its own family until absolute expiry. All deadlines are checked at use, including the absolute family lifetime. Ordinary absolute/access expiry returns `expired` for identity/activation and `reauth_required` for refresh; it does not set family revocation state. Explicit family revocation or account status/epoch invalidation takes precedence if it coexists with expiry. Private access stays denied. The default 5-minute activation, 15-minute access, 30-day refresh inactivity, and 90-day absolute limits are configurable server defaults, not approved production policy.
- F3: activation session IDs and refresh operation IDs are parsed against their existing wire contracts and canonicalized to lowercase before JavaScript comparison or refresh-operation persistence/query. Activation returns the canonical session ID from the looked-up family. This preserves accepted uppercase/mixed-case UUID spellings, PostgreSQL UUID identity and distinct-operation replay handling. Opaque credential tokens and historical domain command serialization/hashes are unchanged. No migration was needed.
- Candidate hash lookup runs through a separate `fitquest_m1c3_lookup` role with fixed-search-path security-definer lookup functions and access to the nonsecret database marker. It cannot select athlete or credential tables. A checked-out `fitquest_m1c3_api` transaction sets an owner context, locks account then family, and rechecks environment, status, epoch, family state, generation, token hash and deadlines before any private domain claim/read/write. The existing `PostgresAthleteRepository` SQL is reused through a session-bound facade; its default fixture facade checks the original fixture environment and queries only columns present in the unchanged M1b database. Forced RLS and owner-qualified queries remain. The new runtime role cannot update account environment or identity; it can lock via the constrained `lock_guard` column. The fixture role cannot see new-account domain rows in the auth-test database.
- `scripts/m1c3-local-db.mjs` creates, migrates and verifies only `rebuild/private-test-artifacts/m1c3-pg/`, its Unix socket on port 55440 and `fitquest_m1c3_auth_test`. It checks an exact filesystem marker, data directory, socket target, in-database marker, known schemas/tables and migration checksums, rejects `DATABASE_URL`, and refuses missing data in an already marked cluster. The read-only validator in `scripts/m1c3-preflight.mjs` is shared by setup/start/verify and the direct auth integration suite. Every `beforeEach` runs the full `verify` command before the authorized test-table `TRUNCATE`. Setup was rerun successfully without resetting data. `scripts/m1b-safe-regression-db.mjs` starts/verifies the previously marked M1b test cluster without invoking its migration/fixture-seed path or touching its development database.

## Verification

- Final F3 `npm run check` from `rebuild/` passed TypeScript checks, ESLint, contract/API builds and **138 default tests** (API 2, contracts 12, mobile 124). `npm run test:pg` passed the **9 existing M1b tests** on `fitquest_m1b_synthetic_test`; `npm run test:pg:auth` passed **24 PostgreSQL tests** on `fitquest_m1c3_auth_test` plus **4 pure preflight tests**. `git diff --check -- rebuild` passed. Node printed its existing experimental SQLite warning. Toolchain: Node 24.12.0, npm 11.6.2, Homebrew PostgreSQL 17.11.
- The auth suite used real PostgreSQL transactions and non-owner/non-superuser/non-BYPASSRLS runtime and lookup roles. It covered concurrent same-identity issuance without orphan accounts, issuance and rotation rollback, committed response loss without bearer replay, pending denial of command/outcome/profile/session/list/identity operations, activation retry and expiry, access/refresh/absolute expiry, crossed/unknown credentials, account status/epoch changes, multiple families, old revocation capability, same/different-operation refresh races, a late same-operation duplicate after activation, direct RLS/privilege checks, and pooled owner-context reset. Test inspection found no issued plaintext token in credential/revocation rows.
- F1 correction tests cover the exact activation/access/refresh boundaries, and a short configured family with an access bearer valid immediately before its absolute deadline. At and after that deadline, identity/activation report expiry, refresh requires reauthentication, and private outcome reads fail. The family remains `active` with `revoked_at` null. Fresh same-account issuance can recover the earlier committed outcome without extending the old family's absolute lifetime. Explicit logout, account disablement and epoch invalidation still report revocation when their condition coexists with expiry. A test-only injected coordinator transport maps an identity-expired outcome to a non-revocation response and maps refresh expiry directly to `reauth_required`; independent local authorization stays accessible and its lock is not called. No mobile runtime adapter was added.
- F2 correction adds four pure negative/positive guard cases using the same validation functions as the database script: changed checksum, unknown ledger entry, wrong filesystem/database marker, redirected target, unknown schema/table. Each negative case proves a cleanup callback is not invoked. The direct auth PostgreSQL suite invokes the full non-mutating script preflight before each test cleanup; the validation reads the exact target and all four checksums. The retained M1b suite and its guarded startup path were unchanged.
- F3 correction adds three real-PostgreSQL tests. An exact valid uppercase operation UUID rotates and then retries harmlessly both before and after successor activation; the consumed UUID is stored canonically and the family remains unrevoked. Lowercase and mixed-case spellings of that UUID are equivalent on the old token and on the next generation, including the account-level reuse check. Concurrent upper/lower requests yield one credential bundle and one reauthentication response without family revocation. A genuinely different operation on the consumed old token still revokes that family while another active family under the same account remains usable. Uppercase activation session IDs work on the initial and successor generations and return the canonical session identity.
- Deterministic barriers held separate PostgreSQL connections while command, profile read, outcome read, refresh and logout competed for the account guard. Work that obtained the guard before logout completed first; work queued after logout failed before a domain claim/read/write. A candidate looked up before revocation was revalidated under the lock. Refresh and logout serialized in both orders; logout could not be undone by a pending successor.
- New repository/pool connections recovered the active generation and an original committed outcome. The task-owned PostgreSQL process was then stopped and restarted through the guarded script: nonsecret counts remained **1 family, 2 generations, 1 outcome** before and after. The compiled default API was briefly run on loopback port 3419: `/health` returned 200 and `/v1/profile` returned 404. That temporary API process was stopped. No auth routes were added.
- The exact test targets were the ignored `rebuild/private-test-artifacts/m1c3-pg/data` cluster, Unix socket directory `rebuild/private-test-artifacts/m1c3-pg/socket`, port 55440, database `fitquest_m1c3_auth_test`; and the retained marked M1b cluster's Unix socket at port 55439 with **only** database `fitquest_m1b_synthetic_test` used by its regression suite. The M1b start path performed marker/ledger verification without migrations or seeds. No TCP PostgreSQL listener, arbitrary connection string, hosted database, real provider, simulator or device was used. Both clusters were started by this task and stopped after the checks; files and data were retained.

## Limits and next task

The provider identity is an injected synthetic test assertion, not an Apple JWT/JWKS or code exchange. No challenge/attempt HTTP flow, real credentials, rate limiting, provider standing check, production audit/cleanup job, auth route, App wiring, native Keychain/SQLCipher session integration, hosted migration or network exposure was added. These tests establish transaction and privilege behavior on the specified local PostgreSQL version; they do not establish provider, native, device or hosted behavior. Authentication failures are repository-local sanitized results/errors and never durable domain rejections. Session logout is not account deletion or provider consent withdrawal. No product AI code was added; D-019 remains a mandatory fresh owner approval checkpoint before any AI implementation.
