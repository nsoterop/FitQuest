# M1c.2 Engineering report — account and local-store boundaries

Date: 2026-09-25. Scope: the authorized local M1c.2 slice under `rebuild/`. This is synthetic test authority and fixture preservation, not real sign-in or full M1c acceptance.

## Implemented boundary

- `apps/mobile/src/ownership.ts` validates explicit UUID-owned synthetic test descriptors with environment, account, store, installation, and local authorization epoch. The new namespace is `fitquest-m1c2-test-<environment>-<account>-<store>-<installation>` for the database, key, and protected record. Its prefix cannot alias the fixture namespace even when the UUID equals fixture A's API account ID. Fixture A/B mapping is explicit and runtime-validated in the same adapter; existing filenames, SecureStore keys, owner values and `m1a.synthetic.v1` marker retain their exact spelling.
- `apps/mobile/src/store.ts` keeps one domain repository for fixture and UUID-owned synthetic test stores. Fixture `open()` and its v1/v2/v3 SQL/checksums remain compatible. `openSyntheticAccountTest()` requires explicit injected database/key resources and trusted test authority; it is Debug-only and has no App entrypoint. Only fresh named test stores receive additive migration v4, with encrypted environment/account/store/installation metadata and a local authorization latch. Existing files with missing keys, missing metadata, changed ownership, incomplete or unknown migrations fail closed without reset. The database encryption key remains separate from authorization and rotating credentials.
- `apps/mobile/src/auth/localLatch.ts` implements an injected protected-record CAS/readback plus a SQLCipher SQLite latch. Private repository reads and transactions require matching authorized bindings on both sides and a current trusted descriptor; transaction checks use Expo's transaction connection. Authorize first writes protected locked, then SQLite locked, then protected authorized, then SQLite authorized. Every intermediate state disagrees or is locked. Logout immediately invalidates the in-memory latch, then attempts SQLite and protected lock writes. A confirmed write on either side is durable lock evidence; if neither succeeds, `apps/mobile/src/auth/durableSwitch.ts` stops sender/visible work and reports `logout_incomplete` without switching. The same switch object can retry durable locking after a transient failure while old work stays stopped; concurrent requests share one lock attempt and only the latest destination callback can run. A failed destination callback is terminal for that switch object because it may have had a partial effect; the caller must reconcile it explicitly. Records, drafts, outbox and keys remain in place. This does **not** claim atomicity across protected storage and SQLite.
- `apps/mobile/src/fixtureSync.ts` now owns the unchanged loopback HTTP transport. The reusable `SyncSender` takes a validated server account UUID from its store, verifies transport identity, and retains stop, eligibility and post-await checks. The repository validates UUID-owned outcomes/receipts using that account UUID rather than A/B inference. Existing App changes are mechanical imports and sender typing; no new screen or real-account runtime access was added.

- F1 tests use the same `DurableAccountSwitch` and real repository/SQLite latch across failed and successful lock attempts, restart, concurrent destination requests, a thrown lock, and a destination callback that throws. Durable lock evidence is required before a destination callback runs. Old private reads stay blocked throughout retries; a callback with a possible partial effect is never replayed automatically.
- F2 tests target each of the four named authorization writes separately for both initially locked and previously authorized stores. The 28 interruption/restart cases cover before write, protected CAS completion, SQLite transaction rollback, SQLite post-commit, and post-readback boundaries. Four more cases inject actual protected or SQLite readback errors. A fully committed dual binding remains authorized if its acknowledgement is lost; a failure before any durable write leaves an existing authorized binding unchanged. ## Limits and next task

The new protected-record adapter and authority are injected test ports. Node SQLite uses the repository transaction calls and a simulated key check, but does not prove native SQLCipher locking, Keychain readback, backup/reinstall installation markers, physical-device protected-data behavior, or a cross-store atomic transaction. If both durable lock writes fail, the caller truthfully reports incomplete logout and blocks switching; the prior authorization may still be present after a crash. A later attempt on the same stopped switch can complete the lock, while a process restart must inspect and resolve the durable state before claiming logout. Native timing-race injection and actual UUID-owned native store access remain unverified. No PostgreSQL or hosted verification was run because API/database code did not change. No Apple provider, session API, real credentials, AI, device configuration, or deployment was added.

Adapter design was checked against current [Expo SQLite guidance](https://docs.expo.dev/versions/latest/sdk/sqlite/) on exclusive transaction scope and SQLCipher keying, and [Expo SecureStore guidance](https://docs.expo.dev/versions/latest/sdk/securestore/) on Keychain persistence and device-only accessibility. These references do not substitute for the deferred native credential and installation-marker verification.

HQ should review M1c.2 and its evidence before assigning M1c.3. The smallest next engineering action is whatever correction HQ identifies in this account/store boundary; no further increment has been started.
